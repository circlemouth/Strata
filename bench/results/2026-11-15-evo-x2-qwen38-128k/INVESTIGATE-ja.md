# EVO-X2のQwen 128K性能差を調査してください

対象リポジトリは https://github.com/circlemouth/Strata 、対象ブランチは `evo-x2-gfx1151` です。
実測と根拠は `bench/results/2026-11-15-evo-x2-qwen38-128k/` にあります。
まずREADME、results.json、data/provenance.json、data/configuration.json、各P1/P2結果とサーバーイベントを読み、登録された値を照合してください。

目的は、期待していた高速化が今回の条件で得られなかった理由を、既存の測定記録とコードから調べることです。
全構成でフォークが遅いとは決めつけず、確認できた事実、原因候補、追加検証が必要な点を分けて報告してください。

比較した実機はEVO-X2、Ryzen AI Max+ 395、128 GB、AMD Radeon 8060S（gfx1151）です。
Aは公式エンジン0.1.58（build ID `7be42963e6be+rocm`）、Cは候補0.1.59.1（commit `1fe214570764e46eba0d4b60c794d83b89cffd62`）です。
上流の基準コミットは `13eedf552417a6a791a7d13c6597e24300ee3a09`、選択的に参照したRDNA3側のコミットは `f557b5440fe345757cae69ede2ed34826da5e612` です。

実入力は130,552トークン、コンテキストは131,072、出力上限は512、キャッシュ利用は0です。
P1は「サーバー2スロットで1件だけ処理」であり、1スロット設定ではありません。
P2は同じ2スロットへ2件同時投入しています。

| 条件 | A | C |
| --- | ---: | ---: |
| P1完了時間 | 233.240秒 | 242.658秒 |
| P1 TTFT | 231.761秒 | 240.742秒 |
| P1 native prefill速度 | 563.6 tok/s | 542.5 tok/s |
| P1 native decode速度 | 27.1 tok/s | 27.2 tok/s |
| P1生成トークン数 | 41 | 53 |
| P2の2件完了時間 | 474.026秒 | 487.668秒 |

P1のprefill速度はCが3.74%低く、decode速度はほぼ同じです。
各条件1回で、自然終了による出力数の違いもあります。
エンジンの世代、サーバー、ビルド条件、資源上限が異なるため、フォーク差だけの因果関係はまだ切り分けられていません。
また、サービス名のiq3sとnative GGUFのUD-IQ3_XXS表記を混同しないでください。

CのP2では、2件目が受理された後、reading開始まで242.915秒待ち、readingから最初のトークンまで241.744秒かかっています。
受付キューでの未受理時間と、受理後のprefill待ちを分け、TTFT全体をprefill時間と呼ばないでください。
今回の2件は完了しましたが、観測されたdecode区間は重なっていません。
以前の480秒設定での片側TimeoutErrorについては、待機とprefillの合計による説明と整合するものの、同等の記録がないため原因確定とは扱わないでください。

A/CのP1ではAMD GPU busy平均が約99.5%、最大100%でした。
GPU利用を維持し、RTXやCPUへの変更を改善策の前提にしないでください。
この値はデバイス全体の使用率で、個別カーネルの所要時間ではありません。

調べてほしい点は次の4点です。

1. 上流版差、フォーク差、ビルド条件、実行時設定を分け、今回のprefillに実際に使われる処理と有効な最適化をコードで追ってください。設定値や候補コードの存在だけで有効と判断しないでください。
2. 128K/P2でprefillが順番待ちになる仕組みを調べてください。request admission、slot割当、prefill処理、decodeとの重なりを区別し、記録と対応する関数、ファイル、行を示してください。
3. KV、prefill chunk、expert cache、メモリ配置、hipBLASLtの調整表、投機生成、CPU制限などについて、約4%のprefill差を説明できる証拠と反証を整理してください。仮説だけなら仮説と明記してください。
4. 同じ上流版の未改変Bを含む比較や、P1/P2を分けた繰り返し試験など、原因を切り分けるための最小限の検証案を示してください。変更する条件、固定する条件、測る指標、成功判定、停止条件を具体的にしてください。

成果物には、結論、根拠、原因候補の優先順位、修正候補、未確認事項、最小検証計画を含めてください。
現在は既存証拠の分析と静的調査までにとどめ、実機推論、再ビルド、サービス停止、設定変更、本番切替を行わないでください。
実機試験や本番採用が必要になったら、その操作と影響を示し、別途承認を得てください。
