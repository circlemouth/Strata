# EVO-X2でのQwen 128K比較実測（2026-11-15）

同じ130,552トークンの入力を1件ずつ処理した比較では、候補Cのprefill速度は現行Aより3.74%低く、生成速度はほぼ同じだった。
2件同時投入の再試験は両方とも完了したが、Cの所要時間はAの先行試験より13.64秒長かった。
各条件1回の非標準ベンチマークであり、フォークの全構成が遅いことや、特定の変更が原因であることは示していない。

## 比較対象と条件

- **A**：公式配布エンジン0.1.58。ビルドIDは `7be42963e6be+rocm`。
- **C**：このフォークの `evo-x2-gfx1151`、コミット `1fe214570764e46eba0d4b60c794d83b89cffd62`。エンジン表示は0.1.59.1。
- **実機**：GMKtec EVO-X2、Ryzen AI Max+ 395、128 GB、AMD Radeon 8060S（gfx1151）。この測定の推論GPUはAMD内蔵GPU。
- **P1**：処理中のリクエストは1件。サーバーは2スロットのままであり、1スロット構成の試験ではない。
- **P2**：同時に2件を投入。サーバーは2スロット。
- コンテキスト上限131,072、実入力130,552、出力上限512、ガード8。合計は131,072。
- A/CのP1は同一リクエストSHA-256。P2も同じ2件を使った。完了した対象リクエストのキャッシュ利用は0トークン。
- temperature=0、top_k=1、top_p=1、seed=42、thinking off。出力は自然終了し、512トークン生成を強制していない。

モデルのサービス名は `strata-qwen3.8-flash-next-iq3s` だが、設定が参照したnative GGUFのファイル名は `Qwen3.8-Flash-Next-UD-IQ3_XXS-00001-of-00004.gguf` である。
既存のpackとnative資産を使った比較であり、この別名だけから純粋なIQ3_S構成と判断しないこと。
重み全体の内容ハッシュは今回の登録時には計算していない。

[設定の抜粋](data/configuration.json)にはKV、prefill chunk、expert cache、投機生成、候補の資源上限を記録した。
Cは16 CPU、104 GiB、swap不可の制限下で動作した一方、Aは既存の制限を維持した。
エンジンの世代、サーバー、ビルド条件も異なるため、A/C差をフォーク変更だけの効果とは扱えない。

## P1の結果

TTFTはクライアントで測った最初の本文トークンまでの時間、prefillとdecodeはエンジンが返したnative timingである。
SSEのヘッダーやheartbeat受信を最初のトークンとは数えない。

| 指標 | A | C |
| --- | ---: | ---: |
| リクエスト完了まで | 233.240秒 | 242.658秒 |
| TTFT | 231.761秒 | 240.742秒 |
| native prefill時間 | 231.660秒 | 240.638秒 |
| native prefill速度 | 563.6 tok/s | 542.5 tok/s |
| native decode速度 | 27.1 tok/s | 27.2 tok/s |
| 生成トークン数 | 41 | 53 |
| キャッシュ利用 | 0 | 0 |

Cはprefill速度が3.74%低く、prefill時間が3.88%長かった。
完了時間は4.04%長かったが、生成トークン数も異なる。
生成速度に明確な差があるとはいえず、出力の正しさや同等性を確認した品質試験でもない。

## P2の結果と待機時間

| 指標 | Aの先行試験 | Cの再試験 |
| --- | ---: | ---: |
| 2件完了まで | 474.026秒 | 487.668秒 |
| 1件目TTFT | 233.940秒 | 242.483秒 |
| 2件目TTFT | 471.248秒 | 484.895秒 |
| 1件目native prefill速度 | 558.2 tok/s | 539.0 tok/s |
| 2件目native prefill速度 | 551.9 tok/s | 540.2 tok/s |
| 1件目native decode速度 | 7.9 tok/s | 5.7 tok/s |
| 2件目native decode速度 | 27.0 tok/s | 26.6 tok/s |
| 合計生成トークン数 | 83 | 94 |
| 2件とも完了 | はい | はい |
| クライアントで観測したdecode区間の重なり | なし | なし |

Cのサーバーイベントでは、2件目は受付後すぐにadmittedとなり、その後、reading開始まで242.915秒待っていた。
reading開始から最初のトークンまでは241.744秒だった。
これはnative prefill時間241.673秒に近いが、計測点が異なるので同じ指標として合算しない。

この約243秒は、受付キューに未受理のまま滞在した時間ではなく、**受理後に入力処理の順番を待った時間**である。
2スロットで2件が完了したことは、2件のprefillやdecodeが同時に進んだ証拠にはならない。
クライアントのTTFT、受理待ち、受理後のprefill待ち、native prefill、decodeを分けて評価する必要がある。

[以前のC試験](data/C-P2-earlier-timeout.json)では、480秒設定のクライアントが片側をTimeoutErrorとして記録し、観測wall時間は483.220秒だった。
今回の待機とprefillの合計は480秒を超えるため、時間予算不足という説明には整合する。
ただし以前の失敗には同等のイベント記録がなく、原因の確定や同一障害の再現とは扱わない。

GPU busyはamdgpuのデバイス全体の値であり、プロセス単位やカーネル単位のプロファイルではない。
